# Danmaku Studio 播放器与全量对齐目标

## 一句话目标

把 Danmaku Studio 从“能编辑弹幕时间轴的工具”推进为一个面向普通用户的弹幕对齐工作台：用户导入 B 站 XML，绑定本地或 Emby 原片，软件能播放、比对、提示版本差异，并把修正后的弹幕安全导出。

最终用户应该能用一句人话理解它：

> 把 B 站删减版弹幕，对齐到我自己的完整版视频上。

## 使用场景

典型用户手里有三类东西：

- B 站 XML 弹幕。
- B 站删减版视频或音频，用来代表弹幕原本对应的时间轴。
- 本地硬盘或 Emby 媒体库里的完整版原片，用来作为最终观看目标。

用户不应该每次都被迫下载整季 Emby 原片到本机。项目应逐步支持“本地文件”和“授权 Emby 媒体”两种来源，并优先用低成本的播放、采样、音频特征和缓存策略完成对齐。

## 产品原则

- 先给用户一条清楚主线：导入弹幕和视频，绑定原片，检查匹配程度，修正版本差异，导出 XML。
- 默认只显示当前步骤需要的操作；高级诊断、参数和实验功能放到展开区。
- 所有用户可见状态都用结果语言：能不能播放、能不能导出、匹配是否可信、哪里需要人工确认。
- 不把内部字段直接扔给用户，例如 `sourceAtMs`、`targetGapMs`、指纹窗口、动态规划阈值只能出现在诊断详情或开发文档。
- 不伪造能力。不能播放 MKV 就明确说当前播放器不支持；没有配置 FFmpeg/mpv 就提示如何配置；Emby 未授权就不显示“可用”状态。
- 原始 XML 和视频内容不被修改；项目只保存媒体引用、编辑状态、缓存索引和非破坏性时间规则。

## 分阶段路线

### G1：默认导出文件夹 / 自定义导出目录

用户问题：每次导出都要临时选位置，不知道文件会去哪，也不方便批量剧集。

交付：

- 设置中心新增“导出”页，支持默认导出目录。
- 导出弹窗允许本次选择其他目录，并清楚显示最终文件名。
- 多集 ZIP 和单集 XML 都遵守同一套目录规则。
- 项目可保存“建议导出目录引用”，但不把用户隐私路径误写进共享导出物。

验收：

- 用户不选择目录时，会导出到默认目录或给出明确引导。
- 导出完成后状态栏显示“已导出到哪里”，并提供打开目录的真实动作。
- 目录不存在、无权限、文件名冲突时有可理解提示。

### G2：Emby 原片绑定项目，不只是查时长

用户问题：现在 Emby 只像一个“查时长工具”，项目不知道自己对应的是哪一部、哪一集、哪个媒体源。

交付：

- 项目模型新增 `mediaBinding` 概念，支持 `localFile` 和 `embyItem`。
- Emby 绑定保存条目 ID、剧名、季集信息、媒体源摘要、运行时长和服务器配置引用。
- Emby 密码、token、临时播放地址不写入项目文件。
- 主界面显示“当前项目绑定的目标原片”，用户能重新绑定或解除绑定。

验收：

- 保存并重新打开项目后，仍能看到绑定的是哪一集。
- Emby 未登录、条目失效、服务器不可达时，项目给出“需要重新连接”的普通语言提示。
- 绑定原片后，后续对齐、预览和导出检查都能读取同一个目标来源。

### G3：B 站 XML 与 Emby 原片的匹配评分和时间轴修正

用户问题：用户不知道这份弹幕和这集原片是否真的匹配，也不知道错位从哪里开始。

交付：

- 新增匹配评分：片名/季集、时长差、弹幕密度、候选锚点、音频/视觉线索共同组成可解释结果。
- 将评分翻译成三类用户结论：很可能匹配、需要确认、看起来不是同一集。
- 对齐结果生成非破坏性提案，而不是直接改时间轴。
- 提案进入时间轴预览，可应用、撤销、导出复核报告。

验收：

- 用户能看到“为什么软件认为它匹配或不匹配”。
- 低置信结果不会自动改项目，只进入人工确认。
- 应用提案后，导出的 XML 时间变化可追溯到具体版本差异或同步规则。

### G4：轻量播放预览，用于实时看效果和打版本差异

用户问题：没有可靠播放，就无法判断弹幕是否对齐，也无法在正确位置标记删减/补时。

交付：

- 保留 HTML Video 作为轻量预览 fallback，明确格式限制。
- 预览区始终显示当前媒体状态：未导入、正在载入、可播放、格式不支持、需要重新连接。
- 播放头、时间轴、弹幕叠加、版本差异标记保持双向同步。
- 用户在当前播放点按快捷键或按钮即可添加“版本差异”，检查器用人话解释影响。

验收：

- 导入 MP4/WebM 后能播放、暂停、拖动、显示弹幕叠加。
- 不能播放的格式不会静默失败，必须说明下一步，例如“请启用 mpv 播放器”。
- 打版本差异后，用户能立刻看到该点之后弹幕整体前移或后移的效果。

### G5：FFmpeg / mpv sidecar 管理能力

用户问题：高码率 MKV、复杂字幕、音轨和硬解不是浏览器 `<video>` 能长期扛住的。

交付：

- 设置中心新增“播放器与工具”页，管理 FFmpeg 和 mpv 路径。
- 支持检测版本、检测可执行文件是否可运行、显示当前使用的播放器后端。
- Tauri 后端提供 sidecar 启动、停止、状态查询和错误报告边界。
- `NativeMpvMediaAdapter` 从占位接口推进到真实实现，但 HTML Video 仍保留为 fallback。

验收：

- 未配置 mpv 时，界面不会假装支持 MKV。
- 配置 mpv 后，本地高码率视频可以由 mpv 播放，并能与应用播放头同步。
- FFmpeg 和 mpv 运行错误能落到用户能处理的提示，而不是只显示技术堆栈。

### G6：音频对齐实用化

用户问题：全量手工标记一整季版本差异太慢，需要软件先找候选位置。

交付：

- 音频对齐支持本地文件和已绑定 Emby 原片两种输入。
- 优先用低成本音频特征发现“完整版比当前版多出的片段”。
- 对候选差异给出时间范围、相差时长、可信度和可播放复核入口。
- 缓存已计算的特征，避免同一集反复全量扫描。

验收：

- 一集视频可以生成候选版本差异列表。
- 用户能逐个试听/预览候选点，接受、跳过或手动修正。
- 接受候选只生成非破坏性版本差异规则，不修改原始 XML。

### G7：逐步播放器化

用户问题：长期目标不是临时预览，而是像专业媒体工具一样承载看、比、修、导出的完整体验。

交付：

- 播放器成为一等模块：媒体源、播放状态、音轨、字幕轨、弹幕轨、缓存和错误状态都有统一模型。
- 支持本地文件、Emby 授权流、未来可能的其他个人媒体库来源。
- 支持双源对比：一边是 B 站删减版参考源，一边是 Emby 原片目标源。
- 支持面向剧集的批量工作台：选中一季，逐集绑定、评分、对齐、复核、导出。

验收：

- 用户可以不理解内部算法，也能完成一季弹幕对齐。
- 播放、对齐、导出形成闭环，失败时知道卡在哪一步。
- 性能目标、缓存策略和错误恢复写入文档并有测试覆盖。

## Emby 能力边界

Emby 相关开发必须先验证公开、授权、稳定的接口能力，再进入产品承诺。后续调研重点：

- 能否通过授权流媒体地址让 mpv 直接播放，而不是整片下载。
- 能否请求转码后的低码率音频或视频片段，用于对齐特征提取。
- 能否请求指定时间点附近的图片或缩略图，用于视觉候选复核。
- 如何处理 token 过期、远程路径不可见、多媒体源、多版本和转码失败。

任何 Emby 实现都必须遵守边界：

- 只访问用户配置且有权限访问的媒体库。
- 不绕过 DRM、账号权限或服务器访问控制。
- 不把密码、token、临时播放 URL 写进项目文件。
- 不能依赖未验证的私有接口作为核心能力。

## 新对话继续开发时先读

新对话开始做播放器或全量对齐时，先按顺序阅读：

1. `AGENTS.md`
2. `progress.md`
3. `docs/player-goal.md`
4. `docs/ARCHITECTURE.md`
5. `README.md`

然后从当前未完成的最低 G 阶段继续。每完成一个可验收阶段：

- 更新 `progress.md`。
- 如果改了可运行代码、UI 或 Tauri，运行相关测试并重新打包 release。
- 创建 Git 提交。
- 关键里程碑创建 `checkpoint/...` 标签。

## 当前优先级

下一步从 G1 开始：先完成默认导出文件夹和自定义导出目录。它风险低、能立刻改善用户体验，也为后续批量剧集导出打基础。
