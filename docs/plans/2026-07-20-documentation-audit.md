# 项目文档体系审计与重写方案

状态：方案存档；阶段 6 已完成用户侧与日常开发文档实施

日期：2026-07-20

适用范围：`AGENTS.md`、`progress.md`、`README.md` 与 `docs/`

> 本文件保存审计结论，避免它长期占用日常 Codex 上下文。它不是当前项目状态；当前状态以根目录 `progress.md`、代码和测试结果为准。

## 结论

当前文档已经能够解释工程能力，但面向的读者混杂：普通用户、维护者、验证人员和 Codex 同时被放进同一批长文档。结果是用户侧 README 过于工程化，内部验收术语又容易进入产品界面；与此同时，Codex 为定位简单任务可能读取过多历史与实现细节。

目标文档体系应满足三点：

1. 用户先知道“这个应用能解决什么、如何完成一次任务”。
2. 开发者能快速找到架构、测试、打包和故障定位资料。
3. Codex 默认只读取短小、稳定、与当前任务直接相关的上下文。

## 审计快照

审计时的仓库概况：

- 384 个 Git 跟踪文件。
- `src/` 约 216 个文件，`src-tauri/` 约 76 个文件。
- TypeScript 测试文件约 94 个，Playwright E2E 规格 2 个，Rust 模块约 19 个。
- 四页主流程已经实际存在：素材、匹配、编辑、导出。
- 人工接管导出已经有真实实现，但 README 中仍存在“只有已验证路径可导出”的旧说法。
- `README.md`、`docs/ARCHITECTURE.md` 与 `docs/PACKAGING.md` 信息量大，职责边界不够清楚。
- 高上下文风险集中在少数超大实现文件，例如原生音频对齐、C137 验收逻辑和大型 React 面板；文档不应要求 Codex为普通任务默认读取这些文件。
- `docs/ux-charter.md` 体量适中、约束清晰，应保留为 UI 决策的最高依据。

## 建议的信息架构

### 根目录

| 文件 | 面向对象 | 内容 |
| --- | --- | --- |
| `README.md` | 用户优先 | 产品价值、适用场景、安装、四步使用指南、常见问题、隐私说明 |
| `AGENTS.md` | Codex/维护者 | 稳定的产品边界、任务路由、工程硬规则、完成定义 |
| `progress.md` | 当前协作 | 当前目标、最近验证、已知风险、下一步；控制在约 80 行内 |
| `CHANGELOG.md` | 用户/维护者 | 按版本记录用户可感知变化 |

### `docs/`

| 文件 | 作用 |
| --- | --- |
| `README.md` | 文档导航，按“我是用户/开发者/验证人员”分流 |
| `USER_GUIDE.md` | 从新建项目到导出 XML 的完整用户教程 |
| `TROUBLESHOOTING.md` | 导入、播放、匹配、导出和 Emby 常见问题 |
| `PRIVACY_AND_DATA.md` | 本地数据、网络访问、项目文件保存内容 |
| `ARCHITECTURE.md` | 稳定的系统边界、数据流、关键模块，而非实现流水账 |
| `DEVELOPMENT.md` | 环境、命令、任务路由、Git/回退方式 |
| `VALIDATION.md` | 测试分层、真实媒体验收、发布门槛 |
| `PACKAGING.md` | Windows/Tauri 构建和发行 |
| `ux-charter.md` | 产品体验宪法 |

### `docs/internals/`

只在相应核心任务中读取：

- `ALIGNMENT_ENGINE.md`：对齐引擎、时间映射和性能约束。
- `EXPORT_TRUST.md`：导出安全门、签名和重新解析验证。
- `C137_ACCEPTANCE.md`：当前精度计划、样本矩阵和退出条件。

### `docs/plans/`

保存未完全实施的方案和历史决策。它明确不属于默认上下文，避免“为了保存历史”与“每次都加载历史”发生冲突。

## README 重写原则

README 首屏应回答：

1. Danmaku Studio 是什么？
2. 它适合什么素材关系？
3. 用户最终得到什么文件？
4. 最短怎样开始？

推荐顺序：

1. 一句话价值说明和一张无本地路径、无测试数据的正式截图。
2. “适合你吗”：原片、参考视频、B 站弹幕 XML 三者关系。
3. Windows 安装与首次启动。
4. 四步指南：导入素材 → 智能匹配 → 检查/校准 → 导出。
5. 一个常见示例：一部长视频对应多集原片。
6. 自动结果与“需要复核”的含义。
7. 数据与隐私。
8. 故障排查入口。
9. 面向开发者的折叠式短入口。

README 不应包含：

- C137、Gold/Beta、HMAC、证据包等内部验收术语。
- 大段架构细节、完整命令矩阵或测试流水。
- 本地绝对路径、演示账号、测试素材名称。
- 把尚未验证的精度指标写成产品承诺。

## AGENTS.md 重写原则

保持短小且稳定，使用“规则 + 路由”而不是项目历史：

- 产品边界和不可破坏的数据原则。
- UI、领域逻辑、测试、打包和文档任务分别读取什么。
- 什么情况下需要读取大文件或历史方案。
- 完成一个变更的最小验证与交付定义。
- 明确 `progress.md` 是当前状态，不是历史日志。

具体实施阶段可以进一步将验收矩阵移入 `docs/VALIDATION.md`，把成熟度项目细节移入 `docs/internals/C137_ACCEPTANCE.md`。

## progress.md 重写原则

只保留：

- 当前目标。
- 最近完成。
- 当前有效的验证结果及其对应提交。
- 已知风险。
- 下一步 3–5 项。
- 历史恢复入口。

所有旧版本可通过 Git 提交、分支和 `checkpoint/...` 标签恢复；不要删除 Git 历史，也不要用覆盖式日志代替版本控制。

## 实施顺序

1. 先建立 `docs/README.md` 和用户/开发者/验证分流。
2. 重写用户侧 `README.md`，并制作不含测试路径的正式截图。
3. 拆分架构、验收与导出信任文档。
4. 精简 `AGENTS.md` 的任务路由，验证 Codex 不再为普通任务读取无关资料。
5. 建立 `CHANGELOG.md`，停止在 `progress.md` 保存发行历史。
6. 检查所有相互链接、命令和产品能力是否与代码一致。

## 验收

- 新用户只阅读 README 就能理解输入、输出和四步操作。
- 开发者能在两次点击内找到启动、测试、打包说明。
- Codex 接到局部任务时，默认上下文不包含历史计划和 C137 大段细节。
- 文档中的所有用户可见入口在当前应用真实存在。
- 旧 `progress.md` 仍可从 Git 历史读取。
- Markdown 链接、命令、截图与版本号经过自动或人工检查。
